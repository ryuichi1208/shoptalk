# 演習ガイド

1回15〜30分を目安に、進行役と対応者を分けて取り組めます。進行役が設定を変更し、対応者はチャット、テナント別指標、JSONログを確認します。観測画面には設定や変更イベントも見えるため、原因を隠した厳密なブラインド演習ではありません。

各演習の開始前に「正常設定へ戻す」を押します。累計値が残るため、開始時点と終了時点の差を比較してください。p95は直近100件なので、回復直後には遅い要求が残ります。新しい要求の結果も併せて見ます。

## 1. 一部の店舗だけ遅い

### 操作

1. `npm run load` を実行します。
2. 「Harbor StoreだけAI応答が遅い」を選んで適用します。
3. 3店舗の失敗件数とp95を比較します。
4. 試行ごとの制限時間を3000msへ変更し、再び観察します。

模擬AIは通常80msで応答します。このシナリオではHarbor Storeだけ2500msかかります。初期設定の1000msではタイムアウトし、最大2回再試行します。MapleとCedarは通常どおり応答します。ただし負荷を増やして共通の受付枠を使い切ると、他店舗にも受付制限が波及します。

### 考えること

- 全体の成功率だけを見ていたら、何を見落とすでしょうか。
- 3000msで応答できても、利用者にとって十分に回復したと言えるでしょうか。
- 原因調査を続ける間、どの情報を誰に共有しますか。

## 2. AI全体の遅延

### 操作

1. 「すべての店舗でAI応答が遅い」を適用します。
2. 実行中の要求、失敗、AI試行数を確認します。
3. 「AIを呼ばず、縮退メッセージを返す」を有効にします。
4. 障害を正常へ戻してから縮退を解除し、新しい要求を確認します。

縮退中はAIへの呼び出しを行いません。画面には、注文変更をまだ受け付けていないことを明示した案内を返します。HTTP 200でも通常の応答とは分けて計測し、受付記録を作りません。

### 考えること

- エラー率の改善だけで、利用者の目的が達成されたと言えるでしょうか。
- 縮退の開始時に、誰の判断やどのような周知が必要でしょうか。
- 縮退を解除する前に、どの条件を確認しますか。

## 3. 依存先の失敗とリトライ

### 操作

1. 「依存先が503を返す」を適用します。
2. 10件程度の要求を送り、AI試行数の増加を確認します。
3. 再試行回数を2から0へ変更します。
4. 同じ件数の要求を送り、試行数とチャットの失敗件数を比較します。
5. 必要に応じて縮退を有効にします。

再試行2回では、失敗するチャット1要求につき模擬AIへ3回アクセスします。再試行0回なら1回です。再試行を止めても依存先の障害は直らず、失敗は続きます。呼び出し倍率は起動後の累計で、受付制限と縮退も分母に含むため、試行数の差分でも確かめてください。

### 考えること

- 一時的な失敗に役立つリトライが、継続する障害ではどのような負担になりますか。
- 再試行を抑える対処と、利用者への影響を減らす対処はそれぞれ何でしょうか。
- 実際のサービスで再試行する前に、冪等性をどう確かめますか。

この演習は依存先への要求増幅を扱います。模擬AIの失敗はスイッチで固定しており、負荷によって障害が自己増幅するフィードバックループ全体を再現しているわけではありません。

## 4. 応答は返るが記録が終わらない

### 操作

1. 「応答後の記録処理が止まる」を適用します。
2. チャットから注文変更の依頼を送ります。
3. 通常応答が返っても、記録待ちが増え、記録完了が進まないことを確認します。
4. 「正常設定へ戻す」を押します。
5. 記録待ちが減り、`record_completed` のイベントが出ることを確認します。

キュー上限は200件です。実行中の要求分も予約するため、記録を待つ要求と処理中の要求の合計が200になると新規受付を制限します。正常時の記録処理は50msに最大1件です。Podを再起動するとメモリ内のキューが失われるため、この演習では設定を戻して処理を再開してください。

### 考えること

- チャットの成功と、業務処理の完了をどう分けて監視しますか。
- 復旧後に未処理の依頼が残っていないことを、何で確かめますか。
- 実環境では、欠損や二重実行をどう防ぎますか。
